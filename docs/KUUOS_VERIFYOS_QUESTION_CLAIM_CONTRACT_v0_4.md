# VerifyOS question-claim contract v0.4

Append-only continuation of v0.3. v0.3 protects a supplied plan against answer-side omissions but does not establish that the plan covers the original question. This module removes the caller-supplied claim plan from the controlled publication path for a closed question language.

The trusted host retains exact original UTF-8 question bytes and binds their SHA256 to v0.2 `context.question_sha256` before execution admission. The compiler accepts five exact registered Japanese questions or canonical JSON such as `{"schema":"kuuos.verifyos.typed-question.v0.4","topics":["rule_inventory","scope_reviews","current_state"]}` (UTF-8, sorted keys, trailing newline). The six topics are snapshot_integrity, rule_inventory, scope_reviews, current_state, authority_limits, full_audit. No whitespace normalization, fuzzy interpretation, model-generated profile or caller-supplied claim list is accepted. A rewritten question must be explicitly treated as a different question. Arbitrary natural language, unknown or duplicate topics and additional fields are HOLD. Trusted host capture, question bytes, policy code, execution environment, independently obtained anchors and key isolation are prerequisites.

Each topic requires the six baseline observations (both gate statuses and exit codes, snapshot sequence and tip), plus its fixed required claims. The compiler takes the union in the v0.3 registry order and records the policy and question digests. In particular withdrawal and obstruction counts cannot be omitted from the rule-inventory topic; fresh current-state questions include current_tip, which remains unsupported. full_audit contains all 13 projections and all five explicitly unsupported claims. All requested claims are preserved, including HOLD. An unavailable admitted bundle produces HOLD rows for the compiled contract, not empty successful coverage. Publication derives the plan again, verifies the v0.3 output, and binds the contract, context and claim packet using the trusted host key. Display recomputes the whole packet; omissions and substitutions are rejected.

```sh
python -B -m runtime.kuuos_verifyos_question_claim_contract_v0_4 compile --question original-question.txt
python -B -m runtime.kuuos_verifyos_question_claim_contract_v0_4 publish --question original-question.txt --request request.json --context context.json --key-file HOST_KEY --evidence-dir PRIVATE_EVIDENCE --prior-packet prior.json > answer.json
python -B -m runtime.kuuos_verifyos_question_claim_contract_v0_4 display --question original-question.txt --request request.json --context context.json --key-file HOST_KEY --evidence-dir PRIVATE_EVIDENCE --prior-packet prior.json --packet answer.json
```

Compile exit 0 means a plan was compiled, not verified. Publish/display exit 0 means ALL_OBSERVED only for this exact registered contract; PARTIAL and HOLD exit 2. The fixed topic policy is a bounded specification, not a theorem of semantic completeness. The 63 nonempty topic subsets and all registered questions are tested; test gates are synthetic pinned scripts executed as real subprocesses. No new Lean proof, proof authority, action authority, external truth, freshness, public attestation, general question understanding or ChatGPT output interception is claimed. No private questions, keys, ledgers or actual private receipts are committed. v0.1-v0.3 and existing Lean sources remain unchanged.
