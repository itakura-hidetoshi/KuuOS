# VerifyOS interpretation anchor v0.10

Append-only extension of v0.9. The independently controlled anchor SQLite file has its own hash-chained journal. The host provisions it exclusively at the independently bound genesis store tip and retains the expected anchor head separately. Each read checks the exact anchor head, seed, schema, chain, transition history and the replayed v0.9 store snapshot. Older, same-height divergent and unanchored newer stores are distinct HOLD states. A correct anchor does not by itself establish any claim evidence.

`initialize(store, anchor, seed, expected_genesis)` is create-only. `prepare(store, anchor, seed, expected_anchor, event_bytes, trusted_event_sha256, next_request, next_context)` checks the current anchor under BEGIN IMMEDIATE, verifies the store against its committed tip and replays the exact proposed revision through v0.8. It writes a PREPARE entry binding the event hash, prior store tip and predicted next store tip. `resume` accepts only the independently retained prepared anchor head and the exact independently admitted event and next context. If the store remains at the previous tip it invokes the existing v0.9 CAS append; if it already equals the intended target it checks and seals without another append. Any other state is HOLD. SEAL is a new anchor row, not an update. While PREPARE is pending all reads for publication HOLD; even a valid target requires explicit recovery. No automatic adoption or reanchoring of arbitrary store tails, no automatic retry or deletion. A storage error with uncertain commit outcome requires reobservation. The host must retain event bytes, trusted event digest and observed anchor heads independently of the store and explicitly resolve a lost acknowledgement from the trusted anchor domain.

`publish_snapshot` requires a matching sealed anchor and store read snapshot before recomputing v0.8 publication. ANCHORED_SNAPSHOT_PACKET_ONLY is a wrapper status, not an evidence pass: the inner packet can be HOLD or ambiguous. This is not a signed store receipt or freshness at delivery. The local tests exercise real SQLite transactions, actual replacement of DB files, a same-height fork, competing processes, an injected failure after store commit before SEAL, and synthetic gate subprocesses. They do not establish power-loss durability or atomicity across databases. PREPARE and SEAL are separate durable transactions, not a distributed atomic commit.

The host must protect the separate anchor file and directory, independently retain the latest expected anchor head, control all compliant writers, capture actual explicit user revisions, isolate keys and trusted runtime, and retain exclusive control over the publication channel. Separate local files are not necessarily independent security domains; if both stores and the independently retained expectation are rolled back together this module cannot detect that. A pending parent state does not distinguish an interrupted pre-append from a rollback to that parent; only the exact authorized intent can be resumed. No external service, distributed consensus, hardware root of trust, public attestation, global replay prevention, user identity, proof/action authority, Lean theorem or ChatGPT integration is claimed. No previous source is changed and no real user data or secrets are committed.
