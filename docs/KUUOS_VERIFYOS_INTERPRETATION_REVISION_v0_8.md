# VerifyOS interpretation revision v0.8

Append-only continuation of v0.7. A verified v0.7 confirmation log is the seed; an independently anchored revision log binds its digest, original family and base context in genesis. Each revision has an exact parent, sequence, unique event ID, original ambiguous span digest, operation and fresh host-supplied request/context. `confirm` requires an open span, `replace` requires the exact current confirmation digest and a different choice, and `retract` requires that digest and a null choice. Each event records the previous confirmation, removed and restored branch IDs. All original branches, seed exclusions and revision history remain visible. Reopening an interpretation does not establish that it is true; exclusion is not refutation.

`replay` takes the original question and candidate, base request/context and log/anchor, revision log/anchor and independently supplied current request/context. Every revision must use a previously unused turn and challenge within the supplied history and the same original question. The final request and context must equal the independently supplied current values. Missing, invalid, stale or contradictory inputs HOLD; a checked prefix is retained but cannot authorize publication. `publish_question` recomputes the v0.6 publication against the current request/context, not the seed context. Original branches and all union claim rows are retained, with active flags and recalculated active requirements. The previous execution receipt cannot be rebound to the new context. `verified_display` checks the exact recomputed packet; only ACTIVE_VIEW_ALL_OBSERVED for the revised bounded view returns 0; PARTIAL, ambiguity and HOLD return 2. The API performs no external operations or mutation of a persistent ledger.

The host must capture actual explicit user revisions, independently retain both log anchors and the current request/context, obtain pinned execution evidence and isolate the key and output channel. A source label or caller-computed digest alone does not authenticate a user. Append-only persistence, global replay prevention, external freshness, third-party attestation and arbitrary-language intent remain unverified; the new context is only distinct in the checked history. No proof or action authority, historical evidence rebinding or ChatGPT integration is granted. Tests use real subprocesses with synthetic pinned gate scripts. Private inputs, keys and receipts are not committed. No previous source or Lean file is changed.
