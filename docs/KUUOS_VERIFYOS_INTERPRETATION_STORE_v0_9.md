# VerifyOS interpretation store v0.9

Append-only extension of v0.8, using the local SQLite transaction pattern of PlanOS v0.53, not replacing that ledger. A trusted host explicitly initializes a new private database for one independently anchored original question and v0.7 seed. No append creates a database. Every stored row binds the seed fingerprint, sequence, previous row digest and exact event; the genesis row has no event. All rows are read in one transaction, schema and chain checked and the reconstructed v0.8 history replayed. The host supplies the original seed, not values obtained from an untrusted database alone.

`initialize(path, seed)` uses exclusive creation; `read(path, seed)` is a read-only snapshot; `append(path, seed, expected_tip, event_bytes, trusted_event_sha256, next_request, next_context)` takes the host's independent event anchor, expected sequence/digest and current-context inputs. BEGIN IMMEDIATE, full chain replay, compare-and-swap against the latest row, v0.8 validation and INSERT occur in one SQLite write transaction. Commit precedes LOCAL_APPEND_COMMITTED. A stale expectation is HOLD, not a merge or implicit retry. Explicit reobservation and a new valid event are required. Failure after INSERT before COMMIT is tested by fault injection; any uncertain storage error requires reobservation, not an assertion that no write occurred. Initialization failure preserves the file for inspection. There is no UPDATE or DELETE in the store API.

`publish_snapshot_at_tip` reads a checked snapshot at the independently expected tip and passes the exact reconstructed v0.8 inputs to the existing publication gate. The wrapper status SNAPSHOT_PACKET_ONLY is not a validation result: the inner packet can be HOLD or ambiguous. It is not a signed store receipt; a trusted host must retain and independently verify the tip and inner packet, and prevent replacement of the output. Later commits may change the active view; there is no claim of freshness at delivery. A prior context receipt cannot satisfy the new v0.8 context. The trusted host must control the DB, its directory, interpreter, input anchors, capture of actual explicit user choices, and isolated keys/output. Logical append-only is not immutable storage: a privileged writer can replace or truncate a DB, and an old consistent prefix is detectable only relative to an independently retained newer tip. Multiple processes sharing one local SQLite file on a filesystem with working SQLite locking are covered; separate databases/hosts, backup rollback, hostile filesystem, distributed consensus, actual power-loss testing, global replay prevention, human identity and atomic cross-system publication remain outside scope. No proof/action authority or ChatGPT interception. Tests exercise synthetic gate subprocesses, actual local transactions and two spawned competing OS processes. No real user data, private ledger or key is committed. Prior modules and Lean sources are unchanged.
