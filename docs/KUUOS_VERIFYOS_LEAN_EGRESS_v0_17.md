# VerifyOS Lean egress v0.17 — research candidate

Append-only extension of the independently verified v0.16 R3 source. This trusted-host API connects actual execution evidence and the raw JSON Lean projection to a closed publication. publication(snapshot, lean, **pair_inputs) accepts the existing v0.13 verifier inputs and a host-selected absolute Lean executable. It recomputes the full diverse audit and both signatures, checks original bundle/request/context digests, reconstructs the existing Python projections for all 18 claim identifiers, checks all signed claim rows, then compiles the four exact SHA256-pinned Lean research modules in a new private temporary directory. The actual CLI is run on the original primary bundle bytes, with the context derived from verified host inputs. No caller-provided admission flag, executable command string, supplied Lean output, or free-form answer is accepted. The entire ordered Lean projection must agree with Python. The packet preserves the signed question-specific claims and branches, answer status and HOLDs, and includes a private execution record with actual subprocess exit codes, toolchain version, source/input/context/observed stdout digests and the full diagnostic projection. Extra audit rows are not additional answer claims.

verified_display recomputes the complete publication, including actual Lean execution, and compares exact packet bytes. A mismatch, unavailable executable, invalid input, prior evidence failure, source drift, or output disagreement is HOLD. Exit 0 is reserved for a matched single active all-observed answer. A matched ambiguous or partial answer still exits 2. This validates the present replay, not whether a claimed earlier execution actually occurred. No cached pass or standalone historical packet suffices. The host must retain the exact verifier inputs independently, provision a trusted Lean installation, control the executable, dependencies, environment and private output channel, and invoke this path at egress. Recording the executable digest and checking the version is not proof of the compiler's authenticity or complete dependency integrity. The CI installs the audited pinned release. This module does not hook ChatGPT, authenticate the user, establish external truth or freshness, certify arbitrary JSON, or prove a complete Python-to-Lean refinement. No new Lean theorem is asserted. Private ledger, question and keys must not be sent to external CI; the tests use only synthetic fixtures and ephemeral keys.

Dedicated sandbox tests exercise actual pinned Lean compilation and projection, fresh display replay, tampered output rejection, common-mode defect rejection before Lean, wrong context, missing witness, source mismatch and invalid host inputs. Separate runner repeats them only after sandbox success. Acceptance conditions are not claimed results before real CI. The prior modules and public formal roots are unchanged; this dependent diagnostic must not be merged into its predecessor branch.
