# VerifyOS contextual method sound coverage v0.14 — research candidate

This additive probe is separate from the existing CodeAI ensemble quorum model and the LivingEngi function-sheaf gluing/overlap-fidelity theorems. It addresses entailment of required answer values from method reports, rather than a quorum or gluing of function sections. The Python v0.13 frozen-profile auditor is a motivation, not a verified implementation of this theory.

Let I be method indices, C contexts, X claims, V values. Separate admitted(i,c,x), scope(i,c,x) and report(i,c,x): Option V. Supported(c,x,y) is existence of an admitted in-scope method reporting y. Honors(valid) is the semantic obligation that every such report is valid in the supplied relation valid: C → X → V → Prop. Forced means all relations honoring those obligations validate the particular claim. The candidate proves Forced iff Supported. The minimal satisfying relation is Supported itself. A missing support admits both a countermodel and a positive model, relative to these positive obligations, so HOLD is not a refutation. Under agreement of the admitted in-scope methods with the candidate answer, forcing every required claim is equivalent to covering every required claim by an admitted in-scope method. A single report is enough only if its separate semantic soundness obligation is met. Different supported values at the same context/claim cannot both fit a functional validity relation. Concrete examples show distinct readout functions sharing 11 at one context despite a reference value of 10, and validity confined to a declared scope.

This is not an unconditional theorem of external truth, cryptographic identity, or Python-gate soundness. The necessary-and-sufficient entailment criterion is relative to the specified class of arbitrary relations; a functional or otherwise restricted semantic model class may entail extra facts. Admission labels do not establish Honors. No verification method is certified sound by its label, by consensus, or by this abstract theorem alone; scope/coverage/semantic soundness and the runtime-to-Lean bridge must be proved separately. No action authority follows.

The research probe imports only Lean core and requires the exact committed Lean toolchain v4.30.0-rc2. The committed mathlib manifest pin is checked but mathlib is not imported. The dedicated workflow first runs strict direct Lean on the exact candidate and audits all 21 named declarations (12 theorems), then invokes actual pinned lean-lsp-mcp 0.30.0 for diagnostics and theorem audits. A separate runner may start only after sandbox success and must re-elaborate the same source and reconcile the first runner's raw MCP evidence. These are verification conditions, not claimed results. The probe remains outside public formal roots until independently certified and separately adopted. Existing proofs and sources are unchanged.
