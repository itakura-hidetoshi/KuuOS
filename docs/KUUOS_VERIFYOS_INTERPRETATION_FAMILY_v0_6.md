# VerifyOS interpretation families v0.6

Append-only extension of v0.5. The host captures original bytes and independently derives a finite family of interpretations, not one preferred paraphrase. The v0.5 exact language is retained. Four registered ambiguous clauses (検査結果, 認証状況, 記録状況, tip) each have two explicitly defined topic choices in the runtime. In the bounded Japanese grammar they can be combined with the prior exact clauses and qualifiers. Each span retains byte offsets, digest and all permitted choices; a current-state prefix or freshness suffix contributes current_state to every interpretation. Unknown or duplicate clauses retain unresolved spans and cause HOLD; malformed input retains an unresolved whole-question span. The Cartesian product is bounded by LIMIT; exceeding it causes HOLD, never truncation. Distinct choice witnesses remain distinct even if their typed plans coincide. No semantic exhaustiveness beyond the registered grammar is claimed.

`compile` produces the candidate family; `check` requires byte-identical canonical family; `issue` requires this check and the exact original question context before running v0.2's trusted execution route. `publish` independently derives the union of required claim IDs, projects evidence once via v0.3, and records the intersection as common required claims. The union is not a single interpretation. Each branch retains its own required IDs, conditional IDs and evidence status; shared rows are referenced by ID in the union. Common requirement does not mean observed truth: a common row can be HOLD. `selected_interpretation` is always null. All observed with multiple interpretations is AMBIGUOUS_ALL_OBSERVED; partly observed with multiple interpretations is AMBIGUOUS_PARTIAL. Both return exit 2, as do PARTIAL and HOLD. Only one registered interpretation with all required rows observed returns exit 0 from publish/display. Compile/check/issue success denotes only the named stage. Missing inputs preserve derivable family and HOLD rows; altered packets, omitted branches and promoted conditional claims are rejected by recomputation. No preference, disambiguation or action authority follows from evidence.

The trusted host must capture original bytes, obtain independent anchors, isolate keys and input snapshots, and own the controlled output path. It must use issue to enforce preflight before the actual execution; an older admitted bundle does not prove historical preflight. The HMAC is a shared-host mechanism, not independent public attestation. The finite test checks 120 questions (15 nonempty subsets of four ambiguous clauses in registry order x two prefixes x two suffixes x optional freshness condition), yielding 640 choice witnesses, not all natural-language interpretations. Tests also use real subprocesses with synthetic pinned gates. No new Lean theorem, open-language semantic completeness, current-state freshness, external truth, new-context validity, proof/action authority or ChatGPT interception is claimed. Private snapshots, receipts and keys are not committed. Predecessor code remains unchanged.
