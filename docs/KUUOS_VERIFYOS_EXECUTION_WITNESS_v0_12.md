# VerifyOS separate-key execution witness v0.12

Append-only extension of v0.11. This is an actual re-execution and signed correspondence path, not a general independent-verifier identity certificate. The verifier independently provisions two distinct raw Ed25519 public keys, the current request/context/anchor, the original seed/revision log, and a policy containing a separate nonce, the exact primary packet SHA256 and the complete expected input inventory. The nonce must differ from the primary challenge. All input files, including base files not directly pinned by v0.1, are bound to the policy. The verifier must obtain these values through trusted channels; deriving them solely from the producer's claims defeats the trust separation.

`execute_and_issue` accepts a snapshot, trusted policy and context, and the executor's private key. It accepts no supplied execution receipt or arbitrary command. It checks the full snapshot inventory and key, executes v0.1's fixed gates under the witness nonce, captures the raw bundle, and signs a role/schema-separated payload using the existing v0.11 Ed25519 envelope. Nonadmitted runs can carry signed HOLD evidence; they do not establish mathematical falsity. `verify_pair` verifies the witness signature and exact projection, independently verifies v0.11's primary packet and history, and requires both admitted receipts to bind the full expected input inventory before and after execution. It rejects reuse of the primary bundle. It compares canonical parsed stdout JSON for both gates, without equating timestamps or paths. Differences yield HOLD with both verified projections and disagreeing gate identifiers retained. Missing or invalid material cannot produce agreement. A successful result is SEPARATE_KEY_EXECUTION_REPORTS_AGREE_ONLY and preserves the primary answer status, including ambiguity and HOLD claims.

Distinct keys, nonce and subprocesses do not prove distinct organizations or isolated machines. A trusted executor must independently obtain its immutable snapshot, control its private key and execution environment, and actually use the issuance route. Both signatures can be forged by colluding or compromised key holders. A shared bad gate can yield identical bad results. No public identity, independent runtime isolation, current-at-delivery freshness, global nonce consumption, truth/proof/action authority, general-language completeness or ChatGPT interception is claimed. The same authenticated pair can be checked repeatedly; the verifier must provision a new nonce for a new observation. The tests use synthetic gates with real subprocesses, real OpenSSL Ed25519, a separate spawned executor and deliberately divergent outputs and nonzero exit codes. All private snapshots, logs and signing keys remain private. No preceding source or Lean file is changed.
